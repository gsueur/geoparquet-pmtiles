One GeoParquet file, with its map inside

A genuine GeoParquet 2.0 file for analytics that also carries the map overviews a web map needs. The full-resolution geometry is stored once, in the Parquet rows, and read from there when you zoom in.

Parcels, MassachusettsLand cover, Europe

Why

Cloud-native vector data usually ships as two files: a GeoParquet for queries and a PMTiles archive for the map. The tiles repeat every feature's geometry at every zoom, so the same features are stored twice, and the two files can drift apart.

The goal here is a single file that

  • stays a standard GeoParquet: DuckDB, GDAL, QGIS, Arrow and any other reader see the same rows, columns, counts and sums;
  • carries real map overviews, generalized the way a cartographer would: simplified, with small features kept visible so dense areas still read as dense;
  • does not duplicate the full-resolution geometry: at close zooms, the map reads it from the Parquet rows.

The layout

GeoParquet rows, 617 MB
PMTiles, 217 MB

The parcels file: PAR1 · row groups and page index · PMTiles archive · footer · PAR1

The PMTiles archive sits between the last data byte and the Parquet footer. Nothing before it moves, so every offset in the footer stays valid. The footer gets one more key-value entry:

pmtiles = {"version": 3, "offset": 616679114, "length": 217318431}

Parquet readers only follow the footer, so they never see the archive. A reader that knows the convention reads the end of the file, finds the entry and opens the archive at its offset. PMTiles offsets are relative to the start of the archive, so the archive is a byte-for-byte copy of a normal .pmtiles file.

How the map reads it

ZoomWhere the map gets it
Overview zoomsBaked PMTiles: features simplified for each zoom, tiny ones kept as small squares so dense areas stay dense.
Detail zoomsThe Parquet rows for 98% of the features: original geometry, turned into vector tiles in the browser. The 2% widest features come from baked tiles (see below).
ClickThe Parquet rows: every attribute of the feature, from the pages that contain the point.
  1. One 64 KB read of the end of the file finds the pmtiles entry. It is the last key-value of the footer, so the rest of the footer is not needed to draw the map.
  2. Overview zooms go through pmtiles.js with a source that adds the archive's offset to every range request. MapLibre works unchanged.
  3. Detail zooms come from a MapLibre custom protocol. A Web Worker reads the footer once, picks the pages whose bounding box overlaps the tile (from the page index of the bbox columns), decodes them with hyparquet, reprojects, then clips and encodes the tile with geojson-vt and vt-pbf. Decoded pages are cached, so neighbouring tiles share them.
  4. Attributes on click use the same page selection on a point: about 60 to 110 KB.

Keeping requests few and parallel. The page index entries of a row group are read in one request and handed to hyparquet, and neighbouring pages are read as one run per column, then cached page by page. Row reads also skip the browser's HTTP cache: Chrome otherwise serializes concurrent range requests to the same URL behind its cache lock, which turned a half-second parcel lookup into five seconds.

Where the line sits

Below the detail zoom, a view holds far more features than it can show: a dense zoom 13 view of Boston covers hundreds of thousands of full-resolution parcels, which tiles show simplified and much lighter. From the detail zoom, tiles are close to full resolution anyway, and they are the heaviest zooms of a normal archive. That is what this file stops storing twice.

The widest 2%

A few features are both very wide and very detailed: water bodies, rights of way, forests, a city's continuous urban fabric. A tile clips them to its square; a Parquet page cannot, it is read whole. In Paris at zoom 12, the regular land cover polygons in view take 0.75 MB of pages, but four pages of polygons wider than 8 km weigh 34.5 MB. The parcels show the same pattern in Boston: 2.2 MB of regular pages, 22.6 MB for two pages of parcels wider than 500 m.

So those features are moved to the end of the file, and for the detail zooms the baked archive carries tiles of these features only. This is the one place where geometry is stored twice, as clipped tiles: 34 MB for the parcels, 338 MB for CORINE, where the widest polygons hold about half of all the geometry. With it, a detail view reads 0.8 MB of rows in Paris and 2.5 MB in Boston.

Pages sized by bytes rather than rows, so that a giant feature sits alone in its page, could remove even that. Writers do not do it today while keeping pages aligned across columns.

The data files

MassGIS Level 3 property tax parcels and CORINE Land Cover 2018, from the Geomermaids parquetry catalogs. To make detail reads tight, the rows were laid out for it:

  • sorted along a Hilbert curve, the widest 2% of features moved to the end;
  • pages of 512 rows with a page index, so a reader can fetch a page, not a whole row group;
  • no dictionary on near-unique identifiers, so a page read does not pull a dictionary as well;
  • native Parquet GEOMETRY with its CRS (GeoParquet 2.0), zstd.

Open questions

  • The page index costs space: 512-row pages make the parcels GeoParquet 617 MB instead of 503 MB, and CORINE 3.11 GB instead of 2.73 GB. Pages sized by bytes could also bring that down.
  • Any tool that rewrites the file drops the archive. That is by design: the map is derived data, like an index.
  • Where the line sits depends on the data: zoom 14 for parcels, 12 for 1:100,000 land cover. Points or small buildings may pay off from a lower zoom.

Related work

The GeoParquet community is discussing overviews, and Cloud-Optimized GeoParquet orders a file's rows by level of detail so that the first row groups make a coarse map. This demo takes another path: the data keeps a purely spatial order for queries, and the overviews are real, generalized map tiles kept next to it in the same file.
